## Objective

Reconcile the closed v0.11.2 architecture contracts with the executable
implementation evidence that still does not exist. This feature registers the
remaining implementation sequence before the exhaustive v0.11.2 milestone QA
gate without reopening historical contract evidence or authorizing execution.

## Evidence Boundary

At the base commit, `iamine-agents` implements only:

```text
root agent.yaml parser and semantic validation
typed always-BLOCKED package-load assessment
typed fail-closed Scope evaluation
typed deny-by-default Permission evaluation after Scope
bounded in-memory audit event projection
```

The package-load assessment always returns 19 unavailable blocker codes. It has
no positive status and cannot consume downstream evidence. There is no agent
runtime crate, package-root reader, sandbox implementation, lifecycle engine,
timeout/cancel implementation, handoff dispatcher, candidate selector, package
loader, execution authorization gate, or runtime executor.

`AGENT-SCOPE-ENFORCEMENT-001`, `AGENT-PERMISSION-ENFORCEMENT-001`, and
`AGENT-AUDIT-EVENTS-001` are executable in-memory boundaries. They remain
deliberately disconnected from package loading and runtime execution.

## Reconciliation Rules

- Existing `CLOSED` contract rows remain closed and historical.
- New implementation rows start as `PROPOSED`.
- A contract row is not executable evidence for its implementation row.
- No feature may remove a blocker owned by another feature.
- Caller booleans, strings, file-existence checks, or manifest self-claims are
  not trusted evidence.
- `iamine-agents` remains the owner of pure package contracts and validators.
- Side-effect-capable behavior belongs in a dedicated `iamine-agent-runtime`
  crate, with narrow modules and a one-way dependency on `iamine-agents`.
- `iamine-node/src/main.rs` may receive wiring only after the runtime executor
  and its field QA are authorized.
- Scheduler, P2P, PubSub, model selection, inference, rewards, reputation, and
  marketplace behavior remain outside this sequence unless a later feature
  explicitly requires and owns an integration.

## Canonical Executable Sequence

### Phase A - Referenced Metadata

1. `AGENT-POLICY-METADATA-VALIDATORS-001`
   - Rust types, generated JSON Schema, bounded YAML parsing, and semantic
     validation for Scope, Permission, and Audit policy references.
   - Separate owner modules are required for each policy family.
2. `AGENT-DESCRIPTIVE-METADATA-VALIDATORS-001`
   - Separate validators for Capability, Expertise, and Resource metadata.
3. `AGENT-BOUNDARY-EVAL-VALIDATOR-001`
   - Positive, negative, refusal, clarification, and handoff boundary fixtures
     with bounded typed validation.

### Phase B - Runtime Foundation And Trust

4. `AGENT-RUNTIME-CORE-001`
   - Introduce the dedicated `iamine-agent-runtime` crate and stable runtime
     owner modules without starting processes or executing agents.
5. `AGENT-PACKAGE-REFERENCE-RESOLVER-001`
   - Bounded package-root containment, path traversal and symlink policy,
     race-aware reads, file count/size limits, and privacy-safe errors.
6. `AGENT-PACKAGE-REVIEW-EVIDENCE-001`
   - Typed local-registry, language-policy, dependency-policy, and explicit
     human-review evidence. Evidence must be non-forgeable by package content.
7. `AGENT-RUNTIME-COMPATIBILITY-GATE-001`
   - Typed runtime-language and resource compatibility decisions. Unknown or
     contradictory metadata remains blocked.

### Phase C - Runtime Enforcement

8. `AGENT-INPUT-OUTPUT-ENFORCEMENT-001`
   - Bounded input/output records, classification, redaction, and fail-closed
     enforcement without persistence or transport assumptions.
9. `AGENT-RUNTIME-SANDBOX-ENFORCEMENT-001`
   - Cross-platform sandbox policy enforcement, resource limits, filesystem and
     network restrictions, and cleanup ownership.
10. `AGENT-EXECUTION-LIFECYCLE-ENGINE-001`
    - Authoritative transition engine for the canonical v0.11.2 states. It does
      not authorize a transition to `running` by itself.
11. `AGENT-TIMEOUT-CANCEL-ENFORCEMENT-001`
    - Bounded timers, cancellation handles, cleanup results, and terminal-state
      evidence.
12. `AGENT-HANDOFF-ENFORCEMENT-001`
    - Typed handoff targets/reasons and dispatcher evidence without permission
      expansion or implicit execution.
13. `AGENT-OUT-OF-SCOPE-RESPONSE-ENFORCEMENT-001`
    - Deterministic refusal, clarification, blocked, and handoff responses kept
      separate from the Scope decision itself.
14. `AGENT-ROUTING-CANDIDATE-SELECTOR-001`
    - Bounded candidate selection from validated task, policy, resource, risk,
      execution-mode, and node-compatibility evidence. No distributed model MoE.
15. `AGENT-AUDIT-EVENT-ENFORCEMENT-001`
    - Connect bounded audit projections to authoritative gate and lifecycle
      outcomes without treating an event as authorization or proof of a side
      effect.

### Phase D - Final Integration

16. `AGENT-EXECUTION-AUTHORIZATION-001`
    - Final typed decision that consumes every independent validated gate. It
      cannot execute, load, install, or persist a package.
17. `AGENT-PACKAGE-LOAD-EVIDENCE-INTEGRATION-001`
    - Replace the static blocker report with a typed evidence assessment while
      preserving all blockers whose owner evidence is absent or invalid.
18. `AGENT-PACKAGE-LOADER-001`
    - Load only an eligible package through the bounded resolver. Loading does
      not imply execution.
19. `AGENT-RUNTIME-EXECUTOR-001`
    - Execute an authorized loaded package through the sandbox, lifecycle,
      timeout, handoff, input/output, routing, and audit owners.

## Risks

- Removing static blockers before their owner evidence exists would create a
  fail-open package path.
- Putting package I/O or runtime behavior in `iamine-agents` would mix pure
  contracts with side effects.
- Putting runtime logic in `iamine-node/src/main.rs` would create a new monolith.
- Combining Scope, Permission, Audit, Sandbox, or Authorization into one gate
  would violate independent-gate architecture.
- Treating a loaded package as executable would bypass final authorization.
- Treating a documentation-only `CLOSED` row as implementation evidence would
  allow the milestone QA gate to start prematurely.
